# Security checklist

Nook is a **web-only Flutter app with no user-data backend**. Everything a traveller saves is stored in a local Drift (SQLite) database on the device (five tables, schema version 7) — there is no account, no sync and no server-side copy of anyone's data. The only outbound calls are to Nook's AI service, YouTube/TikTok oEmbed, the YouTube Data API, the Meta Graph API and the OpenStreetMap tile server.

One service does exist, in `server/`, and it holds exactly one thing: the Anthropic API key. It stores no user data, has no database and keeps no logs of request content. It exists because a Flutter web build is public in full, so a billable key cannot be in one — the reasoning is in `docs/06-security-and-privacy.md`. That shape is why several rows below are N/A, and each one says so.

## GitHub Actions

The repository has exactly one workflow, `.github/workflows/deploy-web.yml`, which builds the web app and publishes it to GitHub Pages.

| # | Check | Yes / No / N/A | Evidence |
| --- | --- | --- | --- |
| 6 | No secret value is written literally in any workflow YAML file | **Yes** | I read `deploy-web.yml` end to end. It contains no key, token or password. Its only `env:` entry is `IS_PRIVATE: ${{ github.event.repository.private }}`, which is a GitHub context value describing repository visibility, not a credential. |
| 7 | Secrets are stored in repository Actions secrets and read with `${{ secrets.NAME }}` | **N/A, deliberately** | The workflow uses no secrets — there is no `secrets.*` reference anywhere in it. It runs `cp .env.example nook.env` before building, so the runner never holds a key and the published build is keyless by construction. This is not an omission but the central decision: **an Actions secret cannot secure a static site.** A secret used at build time is compiled into the output, and the output is what GitHub Pages serves, so marking it secret only hides it from the build log. The key therefore lives on Nook's AI service instead, set with `wrangler secret put` and never read back. The workflow's one `vars.*` reference, `NOOK_AI_BACKEND`, is that service's public address — a variable rather than a secret precisely because it is meant to be published. |
| 8 | No workflow step echoes, dumps or debug-prints a secret, and I opened a recent run's log to confirm | **Yes** | There is no secret in the workflow to print. The four `echo` lines write `ready=true/false` to `$GITHUB_OUTPUT` and emit a `::notice` and a `::warning` about a missing `pubspec.yaml` and private-repo visibility. Scope of what I checked: I read the YAML itself. I did **not** open a run log, because GitHub Actions logs are not reachable from the environment I verified this in. |
| 9 | If I build a signed APK: the keystore is a base64 secret decoded to a file at build time, never printed | **N/A** | This project builds no APK. It is web-only — there is no `android/`, `ios/`, `macos/`, `windows/` or `linux/` directory, and the workflow's only build step is `flutter build web --release`. |
| 10 | Uploaded build artifacts contain no key file, keystore or generated config | **Yes, and now checked mechanically** | The artifact is `path: build/web` from `actions/upload-pages-artifact@v5`. The only configuration file inside it is the `nook.env` the workflow created from `.env.example` moments earlier; I built the project the way the workflow does and confirmed the bundled copy contains exactly `AI_BACKEND_URL=` and `CLAUDE_MODEL=`, both empty. No keystore or signing config exists in this project to be swept in. The new part is that this is no longer taken on trust: the step immediately before the upload runs `./tool/check_bundle.sh build/web`, which scans every file about to be served and fails the run on a credential. |
| 11 | Third-party actions are pinned to a commit SHA, not a moveable tag | **No** | All four are pinned to version tags rather than SHAs: `actions/checkout@v7`, `subosito/flutter-action@v2`, `actions/upload-pages-artifact@v5` and `actions/deploy-pages@v5`. The exposure is limited — the workflow holds no secrets for a compromised action to steal — but it could still alter what gets published. |

## Backend and security rules

Nook has **no backend holding user data**: no Firebase, no Supabase, no database credentials, no account system. Rows 13–15 and 17 are N/A for that reason, and remain so after the AI service was added — that service stores nothing. It receives a request, attaches the key, forwards it to Anthropic and returns the answer; it has no database, no user records and nothing to apply access rules to. Its own surface is bounded by an allowlist instead, documented in `server/README.md`: permitted fields, permitted models, a required Nook tool, an output-token ceiling, a body-size cap and a per-IP rate limit.

| # | Check | Yes / No / N/A | Evidence |
| --- | --- | --- | --- |
| 13 | Firestore and Storage rules are not left open to anyone; they require an authenticated user | **N/A** | There is no Firebase in this project — no `firebase_core` or `cloud_firestore` in `pubspec.yaml`, no `google-services.json`, no rules file. Storage is a local Drift/SQLite database created on first launch (`lib/data/database.dart`). |
| 14 | Rules restrict a user to their own documents where that makes sense | **N/A** | Same reason. There is no shared datastore and no second user: the database lives on the device and holds exactly one local profile. |
| 15 | If Supabase: Row Level Security is on for every table | **N/A** | Supabase was considered in the proposal and deliberately rejected in favour of on-device Drift. There is no Supabase client in `pubspec.yaml` and no project to configure RLS on. |

## Input and app surface

| # | Check | Yes / No / N/A | Evidence |
| --- | --- | --- | --- |
| 19 | Input is validated before it is written, not only styled as valid in the UI | **Yes** | Checked each write path. The profile name is trimmed and must be non-empty before `saveProfile` runs (`profile_setup_screen.dart:50,71`). What the bundle does carry is the AI service's address, which is public by necessity. The limit worth stating plainly: a `--dart-define` is compiled into `main.dart.js` like any other constant, so a build made locally *with* a key has that key in its own output. That is a property of client-side Flutter, not something the arrangement here removes — what it does is make sure such a build is never the published one, by passing no credential on the deploy and by failing the run if `tool/check_bundle.sh` finds one. I confirmed that too, by building with a key and watching the guard refuse it. |

## Anything I found and fixed

This checklist caught four things I had not written down before, and none of them is an exposed credential. The real finding is **row 11**: all four GitHub Actions are pinned to moveable version tags rather than commit SHAs, which is a supply-chain gap I had not considered — it is narrow here because the workflow holds no secrets, but a repointed tag could still change what gets published, and pinning them is a small edit I have not yet made. **Rows 12 and 16** I marked No rather than guessing: secret scanning and push protection, and whether the Google key is API-restricted in the Cloud console, are settings outside the repository that I could not verify from where I ran these checks, so I have not claimed them. **Row 24** turned up a smaller gap — the seeded destination photographs come from Wikimedia Commons and are freely licensed, but I never added them to the README credits list.

What came back clean, and how I checked it: no credential has ever been committed on any branch (searched the full history for added `.env` paths and for Google, Meta and generic key shapes in diffs); no key, token or password is hardcoded in `lib/`; there is no keystore or signing material; the repository contains no student number, personal email, phone number or address, and none in any commit message; every dependency comes from pub.dev with `build/` and `.dart_tool/` ignored; and every write path validates its input before it reaches the database. The two code issues the earlier audit left open have since been fixed, both by changing the behaviour rather than softening the wording: `clearAll()` now clears `app_settings` as well, so "this erases everything on this device" is true and a device handed on comes back at defaults; and "Export Data" now writes every column rather than the fifteen-short subset it did while its own comment claimed otherwise.
