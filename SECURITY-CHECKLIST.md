# Security checklist

Nook is a **web-only Flutter app with no backend**. Everything is stored in a local Drift (SQLite) database on the device (five tables, schema version 7), and the only outbound calls are to Gemini, YouTube/TikTok oEmbed, the Meta Graph API and the OpenStreetMap tile server. That shape is why several rows below are N/A, and each one says so.

## GitHub Actions

The repository has exactly one workflow, `.github/workflows/deploy-web.yml`, which builds the web app and publishes it to GitHub Pages.

| # | Check | Yes / No / N/A | Evidence |

| 6 | No secret value is written literally in any workflow YAML file | **Yes** | I read `deploy-web.yml` end to end. It contains no key, token or password. | 9 | If I build a signed APK: the keystore is a base64 secret decoded to a file at build time, never printed | **N/A** | This project builds no APK. ## Backend and security rules

Nook has **no backend of its own**: no Firebase, no Supabase, no server, no database credentials, and no backend URL anywhere in the repository. Rows 13–15 and 17 are N/A for that reason.

| 13 | Firestore and Storage rules are not left open to anyone; they require an authenticated user | **N/A** | There is no Firebase in this project — no `firebase_core` or `cloud_firestore` in `pubspec.yaml`, no `google-services.json`, no rules file. Storage is a local Drift/SQLite database created on first launch (`lib/data/database.dart`). |
| 14 | Rules restrict a user to their own documents where that makes sense | **N/A** | Same reason. There is no shared datastore and no second user: the database lives on the device and holds exactly one local profile. |
| 15 | If Supabase: Row Level Security is on for every table | **N/A** | Supabase was considered in the proposal and deliberately rejected in favour of on-device Drift. There is no Supabase client in `pubspec.yaml` and no project to configure RLS on. |
| 16 | Firebase and Google API keys are restricted in the Google Cloud console to the APIs and app they are for | **No** | Not verified. ## Input and app surface

| # | Check | Yes / No / N/A | Evidence |
| --- | --- | --- | --- |
| 19 | Input is validated before it is written, not only styled as valid in the UI | **Yes** | Checked each write path. The profile name is trimmed and must be non-empty before `saveProfile` runs (`profile_setup_screen.dart:50,71`). A trip name is trimmed in `showTripDialog` and returns `null` when empty, so `createTrip` is never reached with a blank name (`nook_dialog.dart:120-123,148-152`). Notes are capped at 500 characters in `NookTextField` (`maxLength: 500`). A pasted URL goes through `Uri.tryParse` before the host is read, and `OpenOriginal.isAvailable` additionally requires an `http`/`https` scheme and a non-empty host before the link can be opened. |
| 20 | Nothing secret is recoverable from the built app, since a shipped binary can be unpacked | **Yes, with a stated limit** | The published build is keyless: the workflow creates `.env` from `.env.example`, so unpacking it yields four empty variables. With no `GEMINI_API_KEY`, `NookAi.createExtractor()` returns `SampleExtractor` and the UI says the data is sample data. The limit worth stating: `flutter_dotenv` bundles `.env` as an asset, so anyone who builds locally *with* a key has that key in their own build output. That is a property of client-side Flutter and is exactly why the deployed build carries none and why real extraction is demonstrated on video instead. |

## Anything I found and fixed

This checklist caught four things I had not written down before, and none of them is an exposed credential. The real finding is **row 11**: all four GitHub Actions are pinned to moveable version tags rather than commit SHAs, which is a supply-chain gap I had not considered — it is narrow here because the workflow holds no secrets, but a repointed tag could still change what gets published, and pinning them is a small edit I have not yet made. **Rows 12 and 16** I marked No rather than guessing: secret scanning and push protection, and whether the Google keys are API-restricted in the Cloud console, are settings outside the repository that I could not verify from where I ran these checks, so I have not claimed them. **Row 24** turned up a smaller gap — the seeded destination photographs come from Wikimedia Commons and are freely licensed, but I never added them to the README credits list.

What came back clean, and how I checked it: no credential has ever been committed on any branch (searched the full history for added `.env` paths and for Google, Meta and generic key shapes in diffs); no key, token or password is hardcoded in `lib/`; there is no keystore or signing material; the repository contains no student number, personal email, phone number or address, and none in any commit message; every dependency comes from pub.dev with `build/` and `.dart_tool/` ignored; and every write path validates its input before it reaches the database. The two code issues the earlier audit left open have since been fixed, both by changing the behaviour rather than softening the wording: `clearAll()` now clears `app_settings` as well, so "this erases everything on this device" is true and a device handed on comes back at defaults; and "Export Data" now writes every column rather than the fifteen-short subset it did while its own comment claimed otherwise.
